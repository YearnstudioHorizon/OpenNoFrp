# 03 产品形态设计

## 概述

OpenNoFrp 在完成技术验证后进入了产品化：以单一 Go 二进制（`opennofrp-server`）同时承载

1. 公网端口监听/转发（规则驱动的 public listener）
2. Client 控制侦听（注册+握手+心跳+规则推送）
3. 内嵌 Web 管理面板（登录、Client 管理、规则增删改与启停、注册 Token、一键安装命令）

端口的开/关完全由面板中规则的 `enabled` 位决定：启用即 listen，禁用即关闭。
"默认堵住端口"是 Server 监听行为层的**软堵塞** —— Server 只监听保留端口
（保留 SSH、其它管理端口）和已启用规则的端口，绝不修改宿主机 iptables/防火墙。

## 身份模型

- 面板管理员：单账号，`admin` + bcrypt 密码哈希（SQLite `admin` 表）。
  首次启动若无 admin 行，生成 18 位随机十六进制密码并打印到 stdout
  和 `<db目录>/opennofrp-initial-password.txt`（0600）。
- Client 注册：面板点击"添加内部机器" → 生成一次性注册 Token（可设 label/TTL）
  → 一键命令 `curl -fsSL http://<panel>/install_client.sh?token=XXX | sudo bash`
  → Client 首次启动用 Token 换发永久 `client_id/client_secret`（bcrypt 哈希存储在 Server）
  → 客户端写入 `/etc/opennofrp/client_credentials.toml`（0600）
  → Token 标记为已用；之后每次重连用 `client_id/client_secret` 握手。

## 规则模型

规则存 SQLite `rules` 表，字段：
`id, client_id, name, protocol(tcp/udp/tcp+udp/http), local_ip, local_port, remote_port, preserve_source_ip, enabled, created_at, domains, path_prefix, offline_page`

`protocol = tcp+udp` 为双栈规则：Server 在同一公网端口上同时开启 TCP 和 UDP 监听，
两者共用同一个 RuleID；每条 stream 的 `StreamMetadata.Transport` 仍是 TCP 或 UDP，
Client 无需特殊处理。

`protocol = http` 为 HTTP 反向代理规则：

- Server 在公网端口上运行用户态 `http.Server` + `httputil.ReverseProxy`，按请求的
  Host（`domains`，逗号分隔，支持 `*.example.com` 通配，留空为兜底）和路径前缀
  （`path_prefix`，最长前缀优先）路由到规则。**多条 HTTP 规则可共享同一公网端口**。
  匹配优先级：精确域名 > 通配域名 > 兜底；同级再按路径前缀长度。无匹配返回 404。
- 原生支持 WebSocket（Upgrade 后退化为双向字节中继）与 SSE（`FlushInterval=-1`，
  不缓冲）。请求会附带 `X-Forwarded-For/Host/Proto` 和 `X-Real-IP`，原始 Host 保持不变。
- 每个 HTTP 请求连接对应一条 TCP yamux stream，`StreamMetadata.flags` 置位
  `FlagDialAck`：Client 拨通本地服务后先回写 1 字节确认（0=成功，1=失败）。
  旧版 Client 不理解该标志，不会回写确认，Server 等待超时（10s）后视为不可用，
  因此 HTTP 规则要求 Client 与 Server 同步升级。
- Client 离线或本地服务拨号失败时，返回 503 + `offline_page`（自定义 HTML，上限 64 KB；
  留空使用内置页面）。
- 真实 IP 提取（`ip_sources`，按优先级逗号分隔）：可选 `remote_addr`、`x-forwarded-for`、
  `x-real-ip`、`cf-connecting-ip`、`true-client-ip`、`x-client-ip`、`forwarded`。依次尝试，
  第一个能解析出合法 IP 的来源生效，否则回退为 TCP 对端地址；留空等同 `remote_addr`。
  `trusted_proxies`（IP/CIDR 列表）非空时，仅当 TCP 对端属于其中才信任请求头，否则忽略并
  剥离入站的 IP 类请求头（防伪造）；XFF/Forwarded 链在可信时从右向左跳过可信代理取值。
- 提取出的 IP 同时用于：① `StreamMetadata.ClientAddr`，Client 在开启 `preserve_source_ip`
  时以该 IP 为源地址伪装拨号，后端 TCP 层看到真实访问者 IP；② 改写发往后端的请求头
  `X-Real-IP`、`X-Forwarded-For`（可信时为 入站链 + 对端地址）、`X-Forwarded-Host`、
  `X-Forwarded-Proto`、`Forwarded: for=...;host=...;proto=...`；`CF-Connecting-IP` 等头可信时原样保留。

端口冲突由应用层 `Store.RuleConflict` 检查（不再有 `UNIQUE(remote_port)` 约束）：

- 非 HTTP 规则之间：传输层（TCP/UDP）重叠即冲突；
- HTTP 规则之间：同端口允许，但 (域名, 路径前缀) 有交集即冲突；
- HTTP 与 tcp / tcp+udp 不能共用端口；HTTP 与纯 udp 可以共用。

此外由 `reserved_ports` 表拦截禁用端口的占用（安装时自动写入 SSH 监听端口；面板可增删）。

面板新建/编辑规则表单分两步：先选择协议（HTTP / TCP / UDP / TCP+UDP），再按协议
显示对应字段（HTTP 额外显示域名、路径前缀、自定义不可用页面）。规则支持编辑
（`POST /rules/{id}/edit`）。

## 数据流与控制流

- Client ↔ Server 之间先建立 TCP 控制连接，握手（注册/绑定后认证）成功后
  用 yamux 建立多路复用。Client 打开唯一一个双工控制流：Client→Server 发心跳，
  Server→Client 发 RulesSnapshot（每个连接握手后推送一次；面板每次规则变更都会推送）。
- Server 为每个公网连接主动打开一条 yamux stream，第一帧是
  `StreamMetadata`（二进制头含 Transport、Client 源 IP:端口、RuleID），
  UDP 流在其后按帧（2 字节长度+载荷）转发数据报。
- Client 的 `rulesync` 根据 RuleID 找规则，再做一次 `DetectPortOwner(LocalPort)`：
  - 宿主进程或 host-network 容器 → 直接 `SpoofedDialer.DialSpoofed`（本机已验证路径）
  - bridge 容器（docker-proxy 场景由 `findContainerPublishingPort` 回退判断）
    → `ContainerNetns.Enter()` + 在该 netns 内 `DialSpoofed` 到 `127.0.0.1:LocalPort`
  - 未知/错误端口属主 → 灰度降级为 plain forwarding 并打印告警。
  - UDP 一律 plain（带 2 字节帧封装），UDP 的源 IP 保留暂不在 v1。

## 安装流程

面板每个"新机器"Token 页面直接显示一行命令，内含 Token；该脚本会自动按架构
下载 `client_bin_dir` 下对应二进制、写配置、装 systemd、启动。
Server 的一键安装（`install/linux-server-install.sh`）负责建用户、写配置、
注册 systemd 单元，首次启动打印初始管理员密码。

## 安全约束

- Server 永不碰宿主机的 iptables/nftables/路由/sysctl/TUN。只有 Client 在
  自己控制的机器上做 TPROXY 系统调优，且为专用 fwmark/表/链注释命名空间，
  路线拆卸靠 `tproxy-teardown` 系统化的 state 文件。
- `reserved_ports` 保证 SSH（及面板 admin 自指定的端口）不会被规则占用。

## 已知 v1 限制

- bridge 容器规则要求 LocalPort 与容器内实际监听端口一致（docker `-p H:C` 中
  H≠C 时，请把该规则的 LocalPort 设为容器内部端口 C。
- UDP 不保留源 IP。
- 容器重启后 Client 下一帧流量会触发重新解析端口属主（新 PID），但针对
  netns 内已安装 sysctls/policy route 的状态表尚未自动清理，需管理员技术操作。
- Docker 自定义网络/多网卡容器的 ingress 接口用 netns 内第一个非 lo 接口推断。
- 静默降级是最大生产风险点，已列入后续：envcheck 新增 setns/CAP_SYS_ADMIN 探测、
  按 netns 生命周期管理 worker、容器重启自动恢复。
