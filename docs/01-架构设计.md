# 架构设计

## 一、整体拓扑

**前提约束**：本地真实服务（网页/API/数据库/游戏服务端等）一律假设**不支持**任何形式的协议改造（不支持解析 Proxy Protocol，不支持任何自定义头部）。因此"让本地服务看到真实客户端 IP"这件事，必须完全由 OpenNoFrp 在本地这一侧透明完成，对本地服务是**零感知、零配置**的。

```
[真实客户端] --TCP/UDP--> [云服务器: OpenNoFrp Server]
                                  |
                                  | 控制隧道 (TCP长连接)
                                  | 承载: 转发原始字节 + 自定义元数据帧(真实源IP:端口)
                                  | ★ 云服务器端纯用户态程序，不涉及任何内核网络操作 ★
                                  v
                          [本地Linux: OpenNoFrp Client]
                                  |
                                  | 【本地兼容层，仅在本地这台机器生效】
                                   | TPROXY (iptables-legacy) + ip rule 策略路由
                                  | Client 用 IP_TRANSPARENT socket 选项
                                  | 以"伪装成真实客户端 IP"的身份连接本地服务
                                  v
                          [本地真实服务]
                    (完全不用做任何修改和配置，
                     accept() 拿到的 socket 对端地址就是真实公网客户端 IP)
```

## 二、和 frp 的关键差异

| 特性 | frp | OpenNoFrp |
|---|---|---|
| 端口转发 | 支持 | 支持 |
| 源IP保留 | 不支持 | 支持，且**目标服务无需任何改造** |
| 全端口映射 | 需逐个配置 `[[proxies]]` | 支持端口范围批量映射 |
| 云服务器端内核操作 | 无 | 无（本项目同样不需要，见下方安全边界） |
| 本地Client端内核操作 | 无 | 有（TPROXY，仅限本地这台可控的机器） |
| 一键安装/卸载 | 无官方脚本 | 提供 |

## 三、方案选型：为什么是"云端零改造 + 本地TPROXY"，而不是 Proxy Protocol 或 TUN 网卡

三种方案的对比：

| 方案 | 是否要求目标服务支持协议 | 云服务器风险 | 本地风险 |
|---|---|---|---|
| Proxy Protocol v2 | ❌ 要求目标服务解析协议头（已否决，你要求兼容任意不支持协议的程序） | 无 | 无（但服务端要适配） |
| 云端 TUN + TPROXY | ✅ 不要求 | 🔴 高（需要改云服务器路由/iptables/nftables，且该服务器已有 20 个 Docker bridge 网络 + iptables-legacy/nftables 混合规则，风险极高） | 低 |
| **本地 Client 端 TPROXY（本方案）** | ✅ 不要求 | **零**（云端只做纯用户态数据转发） | 中（TPROXY 配置在本地这台你完全可控的机器上，配置错误最坏情况是重启该机器/回退配置，不存在"永久失联"风险） |

**核心思路**：把所有需要动内核网络栈的操作，全部下沉到本地那台可控的 Linux 机器上执行；云服务器端永远只做最简单的"收字节、转发字节、附带一小段元数据"，风险敞口降到最低。

1. 云服务器只运行一个纯用户态的 TCP/UDP 转发程序，`accept()`/`recvfrom()` 拿到连接后，把原始客户端 IP:端口作为一小段自定义元数据，随数据流一起发给本地 Client。全程不需要 root 权限（监听 1024 以上端口时），不修改路由表、不新增 iptables/nftables 规则、不新增网卡。

2. 本地 Client 收到元数据+数据流后，用 Linux 的 **TPROXY**（`iptables-legacy` 的 `tproxy` target）机制，配合一条本地 `ip rule` 策略路由，让内核把 Client 发出的、目的地是"本地服务真实监听地址"的包，正确路由到 Client 自己（而不是真的发到网络上）。Client 使用 `IP_TRANSPARENT` socket 选项，绑定"伪装的真实客户端 IP"作为源地址去连接本地服务，本地服务的 `accept()`/`recvfrom()` 因此天然拿到真实客户端 IP，全程无需修改本地服务任何代码或配置。

3. TPROXY 是 Linux 内核为透明代理场景原生设计的机制（Squid、Envoy 等成熟软件都在用），且**只需要在本地 Client 所在的这台机器上配置**，与云服务器完全无关。即使本地这台机器的 TPROXY 规则配置出错，最坏情况是本地转发功能不可用，通过 SSH/物理访问该机器修复即可，不存在"断了就再也连不上"的风险。

## 五、控制隧道协议（初步设计，待细化）

- Server 监听控制端口（默认 17000），等待 Client 连入
- Client 主动连接 Server（和 frpc 的行为一致，这样即使本地在 NAT 后面也能建立连接）
- 鉴权：复用 token 机制（不要和现有 frp 的 token 共用，避免混淆）
- 心跳：Client 每 N 秒发送心跳，Server 超时未收到心跳则标记该 Client 离线（用于后续 watchdog 判断）
- 数据通道：每个外部连接（TCP 或 UDP）对应一个逻辑流（yamux 或类似的多路复用库承载 TCP 部分；UDP 单独设计基于四元组的会话表），流内先发送一个自定义元数据帧（协议版本、传输层类型 TCP/UDP、原始客户端 IP、原始客户端端口、目标端口），再转发原始字节。这个元数据帧是 OpenNoFrp 内部私有格式，不要求任何外部标准，不需要目标服务认识它。

## 六、Docker 容器兼容性（重要限制，已在隔离沙箱中充分验证）

本节结论来自在完全隔离的 KVM 虚拟机沙箱（Debian 12，与生产服务器物理隔离）中对 TPROXY + CONNMARK 方案与 Docker 的交互做的系统性验证。验证过程中始终通过 `virsh console`/`qemu-guest-agent` 操作，未触碰宿主机或生产服务的任何配置。

### 6.1 核心技术路线（已验证可行）

基础 TPROXY + `iptables-legacy`（非 nftables）+ `CONNMARK --save-mark`/`--restore-mark` 组合，在"裸进程"场景（本地服务直接监听在宿主机网络命名空间，不经过任何容器）下**完全验证通过**：外部连接方的真实源 IP 能够被本地服务在完全无改造的情况下，通过 `accept()` 正确拿到。

关键坑点记录（供后续实现 Client 时参考，避免重复踩坑）：
- **必须用 `iptables-legacy`，不要用 nftables 原生语法**：在 Debian 12 + 内核 6.1.0 上，用 nftables 的 `type route hook output` 配合 `ct mark`/`meta mark set` 来让 SYN-ACK 回包重新计算路由，存在一个未定位根因的内核/nftables版本缺陷——只要有规则命中"SYN-ACK 回复方向"（`sport` 匹配）并改写 mark，会直接破坏最初的 TPROXY 入站拦截本身（即使匹配条件理论上不该触及入站包）。`iptables-legacy` 的经典 `CONNMARK save/restore` 模式完全没有这个问题，必须作为标准实现方案。
- **必须同时开启多个 sysctl**，缺一个都会导致连接挂死或内核丢包：`net.ipv4.conf.<iface>.route_localnet=1`、`accept_local=1`、`rp_filter=0`（对 `lo`、物理网卡、以及后续涉及到的每个网络接口都要设置，`all` 和单接口都要设）。
- 不要在 `prerouting` 和"回包方向"的同一条规则里既用 `ct mark` 匹配又用 `ct mark` 赋值（自引用），虽然这不是本次问题的根因，但会引入额外的不确定性。

### 6.2 Docker 容器场景（第一轮结论，已被 6.5 节的 netns-worker 方案推翻，保留记录供参考）

**`--network host` 模式：✅ 完全兼容，无需任何特殊处理。**
容器与宿主机共享网络命名空间，从 TPROXY 的视角看和裸进程完全等价，已完整验证通过（外部连接方的真实 IP 被容器内服务正确拿到）。

**默认 bridge 模式（`docker run -p`）：第一轮测试判定为不兼容——这个判断后来被证明是错误的，见 6.5 节。**
第一轮测试里，TPROXY 代理进程运行在**宿主机**的网络命名空间，尝试把流量转发给**容器**的 `docker0` 网桥地址（即跨网络命名空间转发）。这种拓扑下遇到：
1. Docker 的 `docker0`/自定义网桥默认对所有经过该网桥的流量做 `MASQUERADE`，会把我们已经伪装好的源 IP 再次覆盖成网桥网关地址。
2. 尝试绕开的多种变体（端口偏移、容器 netns 内部署代理但使用手工 shell 脚本调试、VM 级代理直连容器 IP、`--network container:` 共享 netns 的 sidecar）都遇到了"`CONNMARK --save-mark` 无法把 mark 写入 conntrack（`conntrack -L` 显示 `mark=0`）"的现象，当时错误地把这个现象归因为"Linux network namespace 本身对 TPROXY + conntrack mark 的交互有内核级限制"。

**这个归因是错的**：见 6.5 节，真正原因是手工调试脚本里缺少 `SO_MARK`（这是后来在 Go 代码真实端到端测试中才发现并修复的一个独立 bug，修复后同样的"容器 netns 内部署代理"拓扑完全跑通）。

### 6.3 macvlan/ipvlan 的验证结论（独立于 6.2，这部分结论依然成立）

在以为 bridge 不可行后，又验证了 **macvlan** 网络模式——这类方案让容器在物理网段上获得完全独立的 MAC/IP，不经过 `docker0` 网桥，天然不存在 MASQUERADE 问题（已验证：宿主机直连 macvlan 容器时，容器确实能看到真实的宿主机 IP，零 NAT）。

但这里发现了一个**真实存在、且依然成立**的内核限制，与 6.2 节的误判是两回事：

- macvlan 驱动有一个已知设计限制——宿主机默认无法直接访问自己创建的 macvlan 子接口。通过额外创建一个 `macvlan-shim` 接口可以绕过这一点。
- 绕过上述限制后，尝试让**宿主机网络命名空间里**的进程伪装成外部 IP、直接 `connect()` 到 macvlan 容器的真实 IP（这是一次**跨命名空间**的伪装尝试，拓扑上等价于 6.2 节第一轮里"代理在宿主机，目标在容器"的模式），结果连接**在用户态 `connect()` 发起阶段就直接失败**（`ip route get` 报 "Network is unreachable"，tcpdump 验证 SYN 包压根没有离开主机任何接口）。
- 排查确认：这不是 `rp_filter` 问题（已验证全部关闭仍不行）。真正原因是 Linux 内核的 **FIB（转发信息库）源地址校验**：内核路由子系统不允许用一个"从未被声明为任何本地接口地址"的 IP 作为出站连接的源地址，这发生在数据包构造之前，与 TPROXY/conntrack/mark 完全无关。连"伪造一条 `local` 路由声明把伪装地址注册为本地地址"这种手法也被拒绝。
- 唯一例外是 `127.0.0.0/8`，通过 `route_localnet` 被特例化处理。

**这部分结论依然成立，结论范围收窄为**：TPROXY + `IP_TRANSPARENT` 源 IP 伪装，**只要代理进程和目标地址不在同一个网络命名空间**（无论中间差的是 docker0 网桥、macvlan 子网，还是任何其他跨 netns 的路径），FIB 校验就会在最基础的层面拒绝这次伪装。这是一条关于"**跨命名空间伪装**"不可行的结论，不是关于"目标在容器里就不可行"的结论——这个区分正是 6.5 节突破的关键。

### 6.5 突破：netns-worker 架构——让代理进程本身搬进容器的网络命名空间（已验证可行，推翻 6.2 节结论）

6.2/6.3 节的所有尝试有一个共同的拓扑假设：**代理进程留在宿主机（或另一个）网络命名空间，目标容器在另一个命名空间，让代理跨命名空间把流量转发进去**。6.3 节证明了这条路径在 FIB 层面走不通。

但还有一个完全不同的拓扑没有测试过：**不要让代理进程留在宿主机命名空间，而是让代理进程本身用 `setns(2)` 搬进目标容器的网络命名空间，代理和目标服务此时共享同一个命名空间，目标地址直接是该命名空间自己的 `127.0.0.1`**——这正是 6.1 节已经验证成功的"裸进程"拓扑，只是把"裸进程所在的命名空间"换成了"容器的命名空间"。

#### 验证过程

1. **最小化 PoC（手工 shell + Python）**：用 `nsenter -t <容器PID> -n` 进入容器的网络命名空间，在命名空间内部署和 6.1 节完全相同的 `iptables-legacy` TPROXY + CONNMARK 规则（接口名换成容器内的 `eth0`，其余逐字一致），并在命名空间内运行一个 Python 写的 TPROXY 转发进程，这次**特别加上了之前遗漏的 `SO_MARK`**。
   - 容器用标准 `docker run -p 9999:9999`（完全不改动任何 Docker 配置）。
   - 从真实的外部宿主机发起连接，容器内目标服务（完全未改造的原生 Python echo）正确看到了宿主机的真实 IP，而不是 `docker0` 网桥地址。
   - 这证明了 6.2 节"bridge 不兼容"的结论是错误的——真正缺的是 `SO_MARK`，不是什么 netns 内核限制。

2. **稳定性压测**：
   - 10 次顺序连接：10/10 成功，每次都正确拿到真实外部 IP。
   - 20 个并发连接：20/20 成功。
   - 全程检查 worker 进程日志和 conntrack 条目，无异常堆积或泄漏。

3. **纯 Go 代码复现（不依赖外部 `nsenter` 进程）**：
   - 用 `golang.org/x/sys/unix.Setns` 系统调用实现了 `client/internal/netnsworker` 包，让 Go 程序自己调用 `setns(2)` 进入容器网络命名空间，复用已有的 `client/internal/tproxy` 模块（同一套 iptables 规则管理、sysctl 管理代码，host 模式和 netns-worker 模式共享实现）。
   - **第一次尝试失败**：用常规的 `go handleConn(conn)` 处理每个新连接，结果新开的 goroutine 创建的上游 socket 跑到了**宿主机**的网络命名空间，而不是容器的，导致 `connect(127.0.0.1:9999)` 连到了宿主机自己的（无人监听的）回环地址，超时失败。
   - **根因（一个 Go 运行时特有的陷阱，Python/nsenter 测试不会遇到）**：`setns(2)` 只影响发起调用的那个 **OS 线程**，不是整个进程。`nsenter` 用 `execve()` 替换整个进程镜像，新进程的所有线程天然都在目标命名空间里。但 Go 的 goroutine 调度器可以把一个未锁定的 goroutine 调度到任意 OS 线程上执行，包括仍停留在宿主机命名空间的线程——哪怕这个 goroutine 是从"已经 setns 成功"的另一个 goroutine 里 `go` 出来的，它自己并不会自动继承那个 setns 状态。
   - **修复**：新增 `netnsworker.ContainerNetns.Enter()` 方法，要求每一个独立调度的 goroutine（特别是每个连接处理 goroutine）在自己的入口处显式调用 `runtime.LockOSThread()` + `setns()`，把自己重新钉死在一个新的、已进入目标命名空间的专属 OS 线程上，而不是依赖"外层 goroutine 已经 setns 过了"这种不成立的假设。
   - 修复后用相同的二进制重新做了 10 次顺序 + 20 次并发测试，**全部成功**，Go 进程的 OS 线程数在 30 次连接后只有 7 个（Go runtime 按文档承诺正确丢弃了用完的锁定线程，没有线程泄漏）。

4. **容器重启场景**（已验证边界行为，生产实现待补全）：
   - `docker restart` 会创建全新的网络命名空间和新的容器 PID。
   - 已验证：指向旧 PID 的 netns-worker 进程在重启后依然存活，但其 TPROXY 拦截**完全失效**（连接会落回 Docker 原生的 DNAT/MASQUERADE 路径，重新看到网桥地址）——这是预期行为，不是 bug。
   - 重新用新 PID 启动一个新的 netns-worker 后，源 IP 保留立即恢复正常。
   - **待办**：生产实现需要监听 Docker 事件（`docker events` 或轮询 `docker inspect`）在容器重启/重建时自动重启对应的 netns-worker，目前只手工验证了"重启后能恢复"，没有做这个自动化。

#### 结论（推翻 6.2 节，收窄并明确了 6.3 节的适用边界）

- **Docker bridge 模式可以保留源 IP，不需要迁移到 `--network host`**，只要 OpenNoFrp Client 把代理进程通过 `setns(2)` 放进目标容器自己的网络命名空间运行。
- 6.3 节 FIB 校验的结论仍然成立，但适用范围是"跨网络命名空间的源 IP 伪装"，不是"容器里的服务就无法保留源 IP"。netns-worker 方案之所以能绕开，是因为它让伪装行为重新回到了"同一命名空间内，目标是 127.0.0.1"这个 FIB 允许的特例。
- 代价：每个开启 `preserve_source_ip` 的 bridge 容器端口，都需要一个独立的 netns-worker（独立的 OS 线程常驻，独立的一套容器内 TPROXY 规则/策略路由/sysctl）。对于同时代理大量容器端口的场景，需要评估线程数量和 `iptables-legacy` 规则管理的开销（每个容器各有一份独立的 mangle 表，互不干扰，但数量多了需要有生命周期管理）。
- 这个方案不需要 `CAP_NET_ADMIN`/`CAP_NET_RAW` 之外的额外权限，但需要能够 `open("/proc/<pid>/ns/net")` 并 `setns`，等价于需要 `CAP_SYS_ADMIN`（或者在部分内核版本/LSM 配置下，`CAP_SYS_PTRACE` 外加目标进程可见性）——这是比纯 host 模式 TPROXY 更高的权限要求，需要在 `envcheck` 里新增对应探测项（**待实现**）。

### 6.6 给用户/项目的建议方案（已更新）

1. **首选，且不再要求用户迁移网络模式**：OpenNoFrp Client 自动检测 `local_port` 所属的进程/容器（`DetectPortOwner`，见 `client/internal/envcheck`），并自动选择部署策略：
   - 宿主机进程 / `--network host` 容器 → 标准 host 命名空间 TPROXY（6.1 节）。
   - bridge/自定义网络容器 → 自动用 netns-worker 方案（6.5 节），`setns` 进入该容器命名空间部署专属 TPROXY。
   - 用户现有的 `docker run -p` 部署**不需要做任何改动**。
2. **次选**（如果 netns-worker 因权限不足或其他原因无法使用）：降级为应用层方案，按目标协议注入真实 IP（如 HTTP 的 `X-Forwarded-For`），需要目标服务能读取。
3. **仍未解决的场景**：容器与宿主机之间如果还隔着更多层网络命名空间嵌套（例如容器套娃、rootless Docker 的 slirp4netns 等用户态网络栈），未经验证，需要单独测试。

## 七、安全边界（再次强调）

**云服务器端**（风险不可控，任何配置错误都可能导致永久失联，因此约束最严）：
- 以非特权用户运行（不需要 root，除非要监听 <1024 的端口）
- 只监听自己配置的端口，不会遍历或修改系统防火墙规则
- 不使用 TPROXY、不使用 TUN/TAP、不修改路由表、不修改 iptables/nftables、不修改内核网络参数
- 卸载时只删除自己创建的 systemd unit 文件和安装目录，不触碰任何其他服务

**本地 Client 端**（风险可控，机器物理可及或至少不是唯一管理入口）：
- 需要 root 权限或 `CAP_NET_ADMIN` + `CAP_NET_RAW` capability（TPROXY 和 `IP_TRANSPARENT` 的硬性要求）
- 会在本地新增：一张独立的 `nftables` 表（专用表名，如 `opennofrp`，不修改任何已有表/链）、一条 `ip rule` 策略路由（专用 fwmark，避免影响已有路由规则）
- 安装/卸载脚本对这些新增规则采用"精确添加、精确删除"，不会用 `flush` 之类的命令清空整个 `nftables`/路由表
- 部署前会检测目标机器上是否已有其他透明代理方案（如已经在用 TPROXY 的其他软件），避免 fwmark/表名冲突
